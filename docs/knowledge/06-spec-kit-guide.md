# 06 — Guide: SDD with GitHub Spec Kit in CalculoIDF

> How Spec-Driven Development is applied in this project, how the drafts are used and where the approval gates are.
> **Version:** Spec Kit 1.2.0 with the Claude Code integration and PowerShell scripts. In that setup the commands are installed as Claude Code skills under `.claude/skills/speckit-*` (`speckit-constitution`, `-specify`, `-clarify`, `-plan`, `-checklist`, `-tasks`, `-analyze`, `-implement`, `-converge`, `-taskstoissues`). Confirm flags with `specify init --help` before initializing.

## 1. The mental model

SDD inverts the code ↔ documentation relationship: the **spec is the primary artifact** and the code is derived from it. In Spec Kit this becomes a pipeline of artifacts separated by level of abstraction:

| Artifact | Answers | Must not contain |
|---|---|---|
| `constitution.md` | Which principles hold for the **whole** project? | Details of one feature |
| `spec.md` | **What** and **why** (users, stories, requirements, success criteria) | Stack, APIs, code structure |
| `plan.md` (+ `research.md`, `data-model.md`, `contracts/`, `quickstart.md`) | **How** (technology, architecture, contracts) | New requirements not foreseen in the spec |
| `tasks.md` | In which **order** and in which verifiable steps | Design decisions |

The hardest — and most valuable — discipline is **keeping the "how" out of the spec**. The drafts follow this: FastAPI, Vite, TypeScript etc. do not appear in the specs; they are in `07-technical-notes-by-feature.md`, which is the **input** to `/speckit-plan`.

## 2. Commands

| Order | Command | Produces |
|---|---|---|
| 1 (once) | `/speckit-constitution` | `.specify/memory/constitution.md` |
| 2 | `/speckit-specify` | branch + `specs/NNN-short-name/spec.md`; active feature in `.specify/feature.json` |
| 2a (optional, recommended) | `/speckit-clarify` | resolves `[NEEDS CLARIFICATION: …]` markers through questions |
| — | **human gate** | spec approval |
| 3 | `/speckit-plan` | `plan.md` and design artifacts |
| 3a (optional) | `/speckit-checklist` | quality checklist for the spec/plan |
| — | **human gate** | plan approval |
| 4 | `/speckit-tasks` | `tasks.md` |
| 4a (recommended) | `/speckit-analyze` | consistency spec ↔ plan ↔ tasks ↔ constitution |
| 5 | `/speckit-implement` | code, following `tasks.md` |
| 5a (optional) | `/speckit-converge` | adds as tasks whatever was left out |

Installation and initialization:

```powershell
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify init --here        # choose the Claude Code integration and PowerShell scripts (see specify init --help)
```

**Where to run `specify init`:** decided in ADR 0002 — at the root of `CalculoIDF_python`.

## 3. How to use the drafts

**Constitution.** Do not overwrite the file generated by `specify init` by copying the draft over it — the Spec Kit template may have evolved. Run `/speckit-constitution` with the draft as input:

> `/speckit-constitution Use the draft at <path>/constitution.md as the basis. Preserve the principles, IDs and rationales; adapt to the current template structure; initial version 1.0.0.`

**Specs.** For each feature, in roadmap order:

> `/speckit-specify <contents of the draft specs/NNN-.../spec.md, or the path to the file>`

Check that the result preserved the stories, FRs, SCs and clarification markers. Then `/speckit-clarify`, review and approval. Only then `/speckit-plan`, passing the matching section of `07-technical-notes-by-feature.md`.

**Language.** All artifacts (constitution, specs, plans, tasks) are written in English. User-facing text quoted inside them (UI labels, error messages shown to users) stays in Brazilian Portuguese. Identifiers (`FR-001`, `SC-001`, `US1`) and the `[NEEDS CLARIFICATION: …]` marker follow the template so the commands recognize them.

## 4. Approval gates (an important adaptation)

An independent comparison observed that Spec Kit **checks that a plan exists, not that a human approved it**. Since the project has a single maintainer, the gate has to be explicit:

- In the header of each spec/plan: `**Status**: Draft` → `Approved (YYYY-MM-DD)`.
- Principle VI of the constitution forbids implementing without that status.
- A separate approval commit (e.g., `docs: approve spec 002`) — visible in the history.

## 5. Adaptations for a brownfield project

Spec Kit is most natural in greenfield projects. Here the system already exists, so:

- `02-current-system.md` plays the role of the "spec of the existing system". Each spec has a **Current system context** section citing the relevant `D-xx` debts.
- Migration specs (002, 003) have the **maintainer** as their main user and **parity** as their central criterion — legitimate, as long as the criteria are measurable.
- For small changes (fixes C-01 to C-03), the full pipeline may be overkill. Options: Spec Kit's lean *preset*, or a short ADR + a PR with a table of numerical differences.

*Recorded trade-off:* OpenSpec models brownfield natively (spec of the current system + changes as deltas). Spec Kit was chosen to learn the full pipeline; if the ceremony weighs too much on small changes, it is worth reevaluating.

## 6. Division of work: Claude Project × Claude Code

| Where | For what |
|---|---|
| **Claude Project** (claude.ai) | Discussing, studying, drafting and reviewing specs/ADRs; domain and architecture questions |
| **Claude Code in the repository** | Running the `/speckit-*` commands, implementing, testing, opening PRs |

**Source of truth:** once a spec is in the repository, **the repository wins**. The Project holds the stable documents (knowledge base, constitution, accepted ADRs); specs in progress are re-sent to the Project when they change in a relevant way. Two copies that diverge are exactly the problem this project is trying to eliminate.

## 7. Definition of done (per feature)

- [ ] Spec approved (no pending `[NEEDS CLARIFICATION]`)
- [ ] Plan approved and consistent with the constitution
- [ ] `/speckit-analyze` with no open inconsistencies
- [ ] Golden files passing (or deliberately updated, with a justification)
- [ ] The feature's new tests passing
- [ ] User documentation (About page / help) updated, if the feature is visible
- [ ] ADR recorded, if there was an architectural decision
- [ ] PR with Conventional Commits, referencing `specs/NNN-…`
